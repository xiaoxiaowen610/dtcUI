## 拍板：a+b 一起做（22:52）
- 用户确认走 A 方案，要求 a（DTCG tokens）与 b（富 registry）一起做；我先评价方向/质量再拍板。
- 代码耦合实测结论（关键依据）：
  - token-resolver 已内置真实别名引擎（aliasRef / cycleDiagnostics / 类型不匹配 / 复用检测），(a) 实际工作量=加 DTCG `$value/$type/$extensions` 解析前端 + `$extends` 主题继承产出 light/dark token 集，内部 resolveTokens 基本不动 → 低-中风险。
  - code-generator 的 `buildHeroProgram` 把 Hero 写死（eyebrow/title/description/actions），页面装配硬编码 `import { Hero }`；但 `buildRegisteredSectionProgram` 是**通用** passthrough（从 example-external-ui 导入任意注册 section + props + data-forge-node-id）。
    - 因此 (b) 分两层：(b1) 加更多 registered sections = 低风险、复用现有通道、demo 体感立刻变厚；(b2) 泛化 Hero/多页面/内联 base 原语 = 高风险，需重构 code-generator+generation-plan+contracts，会威胁 validate:flagship。
  - 生成产物当前硬编码 `color-scheme: dark`，无任何主题开关/light token → (c) light/dark 依赖 (a) 的 token 集才有意义。
- 拍板结论：批准 a+b 作为同一里程碑，但**必须按 a → c → b1 → [b2 可选] 顺序**，不能真并行（否则 b 先建 40 组件后 a 改 token 要回改全部组件）。(b1)+(c) 已能消除“薄”的核心观感；b2（多页面）是可选抛光，建议延后。
- 定义完成（Definition of Done）：每步结束都必须 `pnpm check`（=typecheck+test）与 `pnpm validate:flagship` 全绿，不允许旗舰测试变红。
